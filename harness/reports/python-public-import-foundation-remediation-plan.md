# Corrected finite F0 remediation task list

> **Status:** Read-only decision support. All child identifiers below are proposed and inactive. This document does not record, activate, implement, regenerate, accept, commit, push, or select any task.

## Inherited decisions

- F0 remains the only selected Phase 3 child. D1–D21, M1, I*, V1, Phase 4, and automatic successors remain inactive.
- F0 is a neutral, task-internal current-fact foundation. It cannot classify routes, decide compatibility, change public contracts, alter dependencies, or touch publication content.
- The three task tools are selected `task_tool` inputs, so their final identities must be bound before the maintained manifest and foundation are regenerated.
- Recursive JSON is permitted only at codec/parser/serializer and immediate external-decode boundaries. Generated domain state must use closed frozen records.
- Existing fixed findings remain regression gates, not reopened implementation scope.
- The active parent F0 writer currently owns every affected path. It must be quiesced before any child writer starts.
- The unrelated manuscript modification and pre-existing fixture/helper debt are excluded and must remain byte-identical.

## Diagnosis and challenge reconciliation

Six children are the smallest sound decomposition:

1. model closure;
2. typed construction;
3. initializer acquisition closure;
4. runtime-file completeness;
5. maintained adversarial validation plus the sole generated-pair refresh; and
6. one final read-only aggregate verifier.

The split between initializer and runtime acquisition is retained because they have different behavioral owners and counterexamples. Their common generator file creates only a serialization edge.

The generated pair cannot be refreshed before the validator reaches final bytes: the selection binds the model, generator, and validator. Therefore the sole maintained regeneration belongs to C5, after all three tools are final. C1–C4 may produce temporary candidates but cannot write maintained generated artifacts.

SCC correctness belongs to a cohesive ActionObject in the model file, not to `DependencyGraphView` intrinsic behavior. It must verify represented components through mathematical mutual reachability rather than reproduce the accepted Phase 2 SCC implementation.

No mandatory slice-review loop is included. C1–C5 have deterministic gates and identity handoffs. C6 performs one consolidated architecture/integration review round and never repairs findings.

## Global launch and serialization rules

Before any child is activated:

1. its Task and schema-v2 ownership manifest must exist and validate;
2. the original F0 writer operation and every predecessor writer must be stopped;
3. predecessor identities and checks must have been handed off;
4. only one of the parent writer, C1, C2, C3, C4, or C5 may be writable;
5. administrative Task, selection, ownership, and projection updates must be isolated from implementation diffs; and
6. no proposed child is activated merely because it has been recorded.

The implementation order is:

```text
parent F0 writer quiesced
  -> C1 closed model
  -> C2 typed construction
  -> C3 initializer acquisition
  -> C4 runtime-file completeness
  -> C5 validator + sole maintained generated-pair refresh
  -> C6 final read-only aggregate verification
```

The C3-to-C4 edge serializes whole-file ownership; runtime completeness does not semantically depend on initializer policy.
