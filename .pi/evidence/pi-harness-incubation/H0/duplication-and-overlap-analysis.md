# H0 duplication and overlap analysis

## Boundary

This analysis recommends later ownership. H0 retires, moves, or rewrites nothing. Historical evidence remains historical even when a reusable primitive is later extracted.

## Overlap groups

### Evidence documentation and ownership grammar

Current participants:

- `.pi/skills/document-research-python/SKILL.md` and its test-evidence reference;
- `.pi/skills/develop-operator-records/`;
- `.pi/skills/audit_evidence_identifiers.py`;
- P1 ownership and evidence-documentation validators;
- `docs/harness/ksdft2effmass.harness.04.md` and `.05.md`.

The accepted generic nucleus is the structured VVUQ/documentation grammar in `document-research-python`. Operator rules are a domain extension. AST and P1 validators are deterministic enforcement or compatibility replay, not competing prose authorities. The prospective `write-research-evidence-tests` skill would duplicate this capability if created independently.

**Recommendation:** extract/update one existing grammar capability; do not create a second editable grammar. H1 defines one resource identity and explicit local/domain extensions.

### Artifact and boundary ownership

The maintained P1 Python/JSON module is recorded as `boundary_owned`, but its tests deliberately retain the `artifact` function surface. The accepted shared grammar treats technical integration as artifact-owned while allowing a descriptive filename that names both sides. The prospective harness page presents boundary-owned as a peer primary type and adds a `boundary` function surface.

**Recommendation:** generic primary ownership kinds are `class_owned` and `artifact_owned`. A genuine public Workflow is class-owned. A technical agreement remains artifact-owned with required `relation_kind` (`intrinsic`, `agreement`, `directional_mapping`, `package_surface`, or similar) and named sides. Preserve P1's `boundary_owned` string through the local compatibility adapter and retain existing `test_artifact__...` names. H0 changes no tests.

### Ownership validators

`validate_task_ownership.py` contains a generic v2 nucleus and a project-specific v1 compatibility branch. P1 and evidence-migration validators repeat heading, field, marker, path, owner, node-map, and ID checks while adding exact historical inventories.

**Recommendation:** H1 specifies generic schema/path/identity/role/acyclicity/result primitives with explicit inputs. Local profiles own `.pi` paths, agent frontmatter, prefixes, markers, filename policies, migration states, P1 inventories, and compatibility branches. Existing validators remain authoritative until H4 shadow parity and cutover authorization.

### Checkpoint procedure and executable record

The checkpoint skill requires identity hashes, attempts, partial effects, validation results, branch/remote/commit/push status, and replay behavior. The current checkpoint schema does not represent those fields, and the validator's resolver dry run is a fixed synthetic Option-B case.

**Recommendation:** H1 separates immutable checkpoint decision content from an operation/result record for compare-and-record and Git durability. It does not put mutable Git clients or execution handles into a checkpoint DataObject.

### Skill identity and Graphify copies

Repository Graphify shadows a global fallback. Seven generic reference files are duplicated byte-for-byte, while the entry, query behavior, version, and repository policy differ. Current validation hashes only `SKILL.md`, not the full referenced resource closure.

**Recommendation:** defer Graphify from the minimal H1 contract. A later resource manifest may record upstream and overlay identities. Do not retire repository or global copies until explicit dispatch semantics and shadow behavior exist.

### Live status prose

Task, chain, AGENTS, documentation, and evidence status prose overlap. `docs/development/agent-control-plane.rst` currently says no successor task is active although H0 is active; `docs/user-guide/index.md` also omits H0.

**Classification:** future `RETIRE_AS_DUPLICATE` applies only to repeated editable live-status prose after a generated/reference-based view is accepted. The documentation files themselves are not retired. During H0, authoritative state remains task/chain/checkpoint records and the stale prose is retained as a finding because docs are read-only.

### Agent-role path inventories

The test agent duplicates a large operator test-path inventory already represented in skills, references, manifests, and tests. Current implementation/test/reviewer roles load operator-specific skills even for CPN work.

**Recommendation:** future generic role descriptors state capabilities and side-effect class; version-2 manifests own exact paths; local profiles select domain extensions. Create harness-specific H2/H3 roles rather than broadening current operator/CPN records.

## Retirement candidates

No current source component is safe to retire now. Later candidates are limited to:

1. duplicated editable status prose after a single derived view exists;
2. generic portions of legacy validators after H4 shadow parity;
3. duplicate skill/resource copies after an explicit manifest, overlay relation, and rollback exist.

Historical scripts, manifests, reviews, node maps, checkpoint decisions, and checksum catalogs are never retirement candidates merely because current routing changes.
